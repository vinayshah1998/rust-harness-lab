How to Build an Agent in Rust

or: The Emperor Has No Clothes, and the Borrow Checker Has Opinions

It's not that hard to build a fully functioning, code-editing agent. It's an LLM, a loop, and enough tokens. That's the whole trick.

This guide is a Rust retelling of Thorsten Ball's How to Build an Agent, which does the same thing in Go. We follow the same path: a chat loop, then read_file, then list_files, then edit_file, and then we watch Claude write and edit code on its own. Then we do two things the original skips: we make the agent safe to leave running, and we test it offline with a fake Claude. We end at about 390 lines of Rust plus a few tests, most of it boilerplate.

There's a second goal here: learning Rust while you do it. Every time the code uses a Rust idea for the first time, such as ownership, enums, Result, closures, or trait objects, a box like this one explains it in terms of the agent we're building and links to the chapter of The Rust Programming Language (“the Book”) that covers it properly.

You don't need to read the linked chapters before continuing. Read the box, type the code, get it running, and come back to the Book when something feels like magic. If you've never written Rust, reading Book chapters 3 and 4 beforehand will make the first section much smoother.

Rust concept · Cargo, crates, and dependencies

cargo is Rust's build tool and package manager. cargo new created a package with src/main.rs, which makes it a binary crate, a program you can run. It also ran git init for you. Libraries are called crates too, and they come from crates.io. cargo add writes them into Cargo.toml, and Cargo.lock records exact versions so your build stays reproducible.

The three crates we're adding:

  • serde converts Rust structs and enums to and from data formats. The derive feature lets us write #[derive(Serialize, Deserialize)] instead of writing conversions by hand.
  • serde_json handles JSON specifically.
  • ureq is a small, blocking HTTP client. Most Rust HTTP clients are async. Async is great, but it's a lot to learn on day one, and our agent does one thing at a time anyway.

Two version numbers matter here, and they're easy to mix up. The compiler version (1.98.1, set by rust-toolchain.toml) picks which release of the tools builds your code. The edition (edition = "2024" in Cargo.toml) picks which set of language rules your crate is written in. A newer compiler can still build older editions.

Warm-up Expressions and semicolons

What does this program print?

fn double(n: i64) -> i64 {
    n * 2;
}

fn main() {
    println!("{}", double(4));
}

Run it in the Rust Playground, but write down your prediction first.

Show the answer

Nothing. It doesn't compile: error[E0308]: mismatched types, expected `i64`, found `()`.

A Rust block's value is its last expression. Adding a semicolon turns an expression into a statement, whose value is (), the empty “unit” value. So n * 2; computes 8, throws it away, and the function returns () even though it promised an i64. The compiler even suggests the fix: help: remove this semicolon to return this value. Without the semicolon, it prints 8.

You'll see this throughout the agent. Agent { api_key } at the end of new and Ok(response.content) at the end of run_inference have no semicolon because they are the return values.

Imports, constants, and main

We read the API key from the environment, build an Agent, and run it. MODEL is Claude Haiku 4.5, which is fast, inexpensive, and good with tools. You can switch to a bigger model later. See where to go next for one catch with newer models.

Rust concept · Result, ?, and expect

Rust has no exceptions. A function that can fail returns Result<T, E>, an enum that is either Ok(value) or Err(error). main returns Result<(), Box<dyn Error>>: on success, nothing ((), the empty tuple); on failure, any kind of error. If main returns an Err, Rust prints it and exits with a non-zero status.

std::env::var returns a Result too. .expect("...") says: “if this is an error, crash right now with this message.” Crashing is called a panic. Panicking is reasonable for a missing API key because the program can't do anything useful without one. Inside the agent we'll use ? instead, which you'll see a lot.

const declares a compile-time constant. Its type, &str, is a borrowed string slice. String literals are baked into the binary, so a constant can point straight at one.

Rust concept · structs, impl, and methods

A struct groups named fields; it's Rust's version of a class without inheritance. Behavior lives in a separate impl block. new doesn't take self, so it's an associated function called as Agent::new(...). By convention it acts as a constructor. Agent { api_key } is field-init shorthand for Agent { api_key: api_key }.

Notice that new takes api_key: String by value. Passing it to new moves the string into the struct. After that, the Agent owns it.

Warm-up Enums that carry data

This enum has two variants that hold different data. What two lines does it print?

#[derive(Debug)]
enum Shape {
    Circle { radius: f64 },
    Square(f64),
}

fn area(shape: &Shape) -> f64 {
    match shape {
        Shape::Circle { radius } => 3.0 * radius * radius,
        Shape::Square(side) => side * side,
    }
}

fn main() {
    let shapes = vec![Shape::Square(2.0), Shape::Circle { radius: 1.0 }];
    for shape in &shapes {
        println!("{shape:?} has area {}", area(shape));
    }
}

Run it in the Rust Playground, but write down your prediction first.

Show the answer

Square(2.0) has area 4
Circle { radius: 1.0 } has area 3

Each variant has its own shape. Square holds one unnamed f64, and Circle holds a named field, exactly like ContentBlock::Text { text } will. A match pattern opens the variant and binds its fields to names. Because we match on a &Shape, radius and side are borrowed &f64s, and arithmetic works on those directly.

A small detail: {shape:?} uses the derived Debug format, which shows 2.0, while {} prints the number 4.0 as plain 4.

Messages as types

The Anthropic Messages API takes a list of messages. Each message has a role ("user" or "assistant") and a list of content blocks. For now, the only kind of block is text. Put these types at the bottom of the file, after the impl block:

#[derive(Serialize, Deserialize, Debug)]
#[serde(rename_all = "lowercase")]
enum Role {
    User,
    Assistant,
}

#[derive(Serialize, Deserialize, Debug)]
struct Message {
    role: Role,
    content: Vec<ContentBlock>,
}

#[derive(Serialize, Deserialize, Debug)]
#[serde(tag = "type", rename_all = "snake_case")]
enum ContentBlock {
    Text { text: String },
}

#[derive(Deserialize, Debug)]
struct Response {
    content: Vec<ContentBlock>,
}

With these attributes, a ContentBlock::Text { text: "hi".into() } serializes to exactly the JSON the API wants:

{"type": "text", "text": "hi"}

Rust concept · enums carry data, and derive writes code for you

Rust enums are much more than named integers. Each variant can hold its own fields, so ContentBlock can say “a block is a Text with a text field, or (soon) a ToolUse with an id, name, and input.” This kind of type is sometimes called a tagged union or sum type, and it's a perfect fit for a JSON object whose "type" field decides which other fields exist.

#[derive(...)] asks the compiler to generate trait implementations. Debug lets us print values with {:?}. Serialize and Deserialize are serde's derive macros, which generate the JSON conversion code at compile time. The #[serde(...)] attributes tune that code: tag = "type" stores the variant name in a "type" field, which serde calls an internally tagged enum, and rename_all turns ToolUse into "tool_use".

Response only declares content. The API sends back more fields, such as id, usage, and stop_reason, and serde ignores the ones we don't ask for.

Warm-up Moving a value

Will this compile? If not, which line fails, and why?

fn main() {
    let reply = vec![String::from("hi")];
    let mut history = Vec::new();
    history.push(reply);
    println!("{}", reply.len());
}

Run it in the Rust Playground, but write down your prediction first.

Show the answer

The last line fails: error[E0382]: borrow of moved value: `reply`.

history.push(reply) takes ownership. The vector now lives inside history, and the name reply no longer owns anything, so there's nothing to ask .len() of. Nothing was copied; ownership was handed over.

The fix is to swap the last two lines: read first, then move. The chat loop below uses exactly this order. It prints Claude's reply through a borrow, for block in &content, and only then moves content into the conversation.

The loop

Now the heart of it. Put run inside impl Agent, and read_line below the impl block as a free function:

    fn run(&self) -> Result<(), Box<dyn Error>> {
        let mut conversation: Vec<Message> = Vec::new();

        println!("Chat with Claude (use 'ctrl-c' to quit)");

        loop {
            print!("\x1b[94mYou\x1b[0m: ");
            io::stdout().flush()?;
            let Some(user_input) = read_line()? else {
                break;
            };
            if user_input.is_empty() {
                continue;
            }
            conversation.push(Message {
                role: Role::User,
                content: vec![ContentBlock::Text { text: user_input }],
            });

            let content = self.run_inference(&conversation)?;

            for block in &content {
                match block {
                    ContentBlock::Text { text } => println!("\x1b[93mClaude\x1b[0m: {text}"),
                }
            }
            conversation.push(Message {
                role: Role::Assistant,
                content,
            });
        }

        Ok(())
    }
fn read_line() -> io::Result<Option<String>> {
    let mut line = String::new();
    if io::stdin().read_line(&mut line)? == 0 {
        return Ok(None);
    }
    Ok(Some(line.trim().to_string()))
}

Print a prompt, read a line, append it to the conversation, send the whole conversation to Claude, print what comes back, append Claude's reply, and go around again. The odd-looking \x1b[94m sequences are terminal color codes.

Rust concept · ownership: move it or borrow it

This loop is a small ownership workout, and it's worth reading slowly.

Mutability is opt-in. let mut conversation can change; a plain let can't. &self means run borrows the agent immutably, so it can read self.api_key but can't change it.

Every value has one owner. let content = self.run_inference(...)? makes content the owner of Claude's reply, a Vec<ContentBlock>. Then:

  1. for block in &content borrows the vector. We only want to look at each block to print it, so we take references (&ContentBlock) and leave ownership with content.
  2. Message { role: Role::Assistant, content } moves the vector into a new Message, and push moves that message into conversation. Nothing is copied; ownership is handed over. After this line, the name content no longer refers to anything.

The order matters: borrow first, then move. Try the experiment below to see what happens otherwise.

Patterns everywhere. let Some(user_input) = read_line()? else { break; }; is let...else. If the pattern matches, user_input is bound and we continue; if not (None, meaning stdin is closed, for example after Ctrl-D), the else block must leave the loop. read_line returns io::Result<Option<String>>: it might fail (Result), and if it succeeds there might not be a line (Option). Rust makes you write down both possibilities in the type.

Traits in scope. flush() is a method of the Write trait. It only works because we wrote use std::io::{self, Write}. We need it because print!, unlike println!, doesn't end the line, so the prompt would otherwise sit in a buffer.

Warm-up The ? operator

What are the two lines of output?

use std::num::ParseIntError;

fn add_strings(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x: i32 = a.parse()?;
    let y: i32 = b.parse()?;
    Ok(x + y)
}

fn main() {
    println!("{:?}", add_strings("2", "3"));
    println!("{:?}", add_strings("2", "three"));
}

Run it in the Rust Playground, but write down your prediction first.

Show the answer

Ok(5)

In the second call, a.parse()? succeeds, then b.parse()? fails, and ? immediately returns that error from add_strings. Ok(x + y) never runs. There's no panic and no exception. The error is an ordinary value that the caller receives and can print.

Talking to Claude

Last piece. This one also goes inside impl Agent, after run:

    fn run_inference(&self, conversation: &[Message]) -> Result<Vec<ContentBlock>, Box<dyn Error>> {
        let body = json!({
            "model": MODEL,
            "max_tokens": 4096,
            "messages": conversation,
        });

        let response: Response = ureq::post(API_URL)
            .header("x-api-key", &self.api_key)
            .header("anthropic-version", "2023-06-01")
            .send_json(&body)?
            .body_mut()
            .read_json()?;

        Ok(response.content)
    }

That's an HTTP POST with two headers and a JSON body. The json! macro builds the body, and because Message implements Serialize, we can drop the whole conversation into it.

Rust concept · slices, ? chains, and type-driven inference

conversation: &[Message] is a slice, a borrowed view of a run of Messages. We call it with &conversation, a &Vec<Message>, and Rust converts it automatically. Accepting &[T] instead of &Vec<T> is idiomatic: it says “I only need to read a sequence.”

Each ? means “if this returned Err, return that error from this function right now.” send_json can fail with a network error or a non-2xx HTTP status; read_json can fail if the body isn't the JSON we expect. ? also converts each concrete error type into our Box<dyn Error>, which is why one return type covers both.

How does read_json() know to produce a Response? It's generic over its output type, and we wrote let response: Response = .... Rust infers the type parameter from the annotation, so a type annotation can choose which code runs.

json! ends in ! because it's a macro, not a function. Macros can accept custom syntax, such as JSON written inline in Rust.

A first tool

What is a tool? You tell the model, “if you want me to do X, reply in this specific format.” When it does, you do X and reply with the result. That's all. Everything else is abstraction on top of that.

It's like telling a friend, “wink if you want me to raise my arm.” We can try it right now, without changing any code:

You: You are a weather expert. When I ask you about the weather in a given location, reply with get_weather(<location_name>). I will then tell you what the weather is. Understood?

Claude: Understood! When you ask about the weather somewhere, I'll reply with get_weather(<location_name>) and wait for you to tell me.

You: Hey, what's the weather in Munich?

Claude: get_weather(Munich)

You: hot and humid, 28 degrees celsius

Claude: Thanks! Munich is hot and humid at 28°C (about 82°F). Stay hydrated, wear light clothing, and plan indoor activities for the hottest part of the day.

Claude winked, we raised our arm, and it used the result. Models are trained to use tools like this and are eager to. The API formalizes the wink. We send tool definitions with each request: a name, a description, and a JSON Schema for the input. When Claude wants to use a tool, it replies with a tool_use block instead of, or in addition to, text. We run the tool and send back a tool_result block. That's the entire protocol.

Warm-up Exhaustive match

main asks about a yellow light, which action doesn't mention. What happens?

enum Light {
    Red,
    Yellow,
    Green,
}

fn action(light: Light) -> &'static str {
    match light {
        Light::Red => "stop",
        Light::Green => "go",
    }
}

fn main() {
    println!("{}", action(Light::Yellow));
}

Run it in the Rust Playground, but write down your prediction first.

Show the answer

It doesn't compile: error[E0004]: non-exhaustive patterns: `Light::Yellow` not covered.

Many languages would compile this and do something surprising at runtime, such as falling through or returning nothing. Rust refuses to build a match that might not handle a value. Add Light::Yellow => "slow down", and it prints slow down.

You're about to hit this same error on ContentBlock when we add the tool variants. That's the compiler showing you where the new cases need handling.

Teach the types about tools

First, update ContentBlock so it knows the two new kinds of blocks. Replace the enum, and add Value to the serde_json import at the top: use serde_json::{Value, json};.

#[derive(Serialize, Deserialize, Debug)]
#[serde(tag = "type", rename_all = "snake_case")]
enum ContentBlock {
    Text {
        text: String,
    },
    ToolUse {
        id: String,
        name: String,
        input: Value,
    },
    ToolResult {
        tool_use_id: String,
        content: String,
        is_error: bool,
    },
}

ToolUse is Claude asking us to run something. Its input is arbitrary JSON, so we keep it as a serde_json::Value and let each tool decide how to read it. ToolResult is our answer. It echoes the request's id as tool_use_id so Claude knows which request it answers.

Now run cargo build:

error[E0004]: non-exhaustive patterns: `&ContentBlock::ToolUse { .. }` and `&ContentBlock::ToolResult { .. }` not covered
  --> src/main.rs
   |
   |                 match block {
   |                       ^^^^^ patterns `&ContentBlock::ToolUse { .. }` and `&ContentBlock::ToolResult { .. }` not covered

In Thorsten's Go version, this is the moment where Claude says “let me read that file for you” and then nothing happens, because the program silently ignores the wink. In Rust, the compiler won't let us ignore it. The match in run handles only Text, and a match must cover every variant. We'll fix that in a minute.

(If you'd sent tools without adding the variant, you'd get a runtime error instead: unknown variant `tool_use`, expected `text`. Strict types fail loudly rather than dropping data.)

Rust concept · exhaustive match

match is Rust's switch, but the compiler checks that you've handled every possible case. When you add a variant to an enum, every match that doesn't handle it becomes a compile error, so you get a to-do list of places to update. That's a big part of why Rust programmers model data with enums.

Define what a tool is

Every tool needs four things: a name, a description that tells the model what it does and when to use it, a JSON Schema for its input, and a function that runs it. Add this struct with the other types:

#[derive(Serialize)]
struct ToolDefinition {
    name: &'static str,
    description: &'static str,
    input_schema: Value,
    #[serde(skip)]
    function: fn(Value) -> Result<String, Box<dyn Error>>,
}

The first three fields are what Claude sees. The API's tool format is {"name", "description", "input_schema"}, so deriving Serialize on this struct produces it directly. The fourth field is the function, which Claude never sees, so #[serde(skip)] leaves it out of the JSON.

Rust concept · function pointers, 'static, and Box<dyn Error>

fn(Value) -> Result<String, Box<dyn Error>> is a function pointer type: “any function that takes a Value and returns a Result of a string.” Functions are values in Rust, so we can store one in a field and call it later. That's our whole tool registry.

&'static str is a string slice that lives for the whole program. 'static is a lifetime. Lifetimes are how the compiler proves a reference never outlives the data it points to. String literals live in the binary, so they're 'static, and storing them in a struct needs no further bookkeeping.

Box<dyn Error> is a trait object: a pointer to some value of an unknown concrete type that implements the Error trait. File errors, JSON errors, and HTTP errors are all different types, and Box<dyn Error> lets one function return any of them.

Write the tool

#[derive(Deserialize)]
struct ReadFileInput {
    path: String,
}

fn read_file_tool() -> ToolDefinition {
    ToolDefinition {
        name: "read_file",
        description: "Read the contents of a given relative file path. Use this when you want to see what's inside a file. Do not use this with directory names.",
        input_schema: json!({
            "type": "object",
            "properties": {
                "path": {
                    "type": "string",
                    "description": "The relative path of a file in the working directory."
                }
            },
            "required": ["path"]
        }),
        function: read_file,
    }
}

fn read_file(input: Value) -> Result<String, Box<dyn Error>> {
    let input: ReadFileInput = serde_json::from_value(input)?;
    let content = fs::read_to_string(checked_path(&input.path)?)?;
    Ok(content)
}

That's one function, read_file, and two descriptions the model reads: one for the tool and one for its path parameter. Add use std::fs; to the imports at the top.

Look at how little read_file does. serde_json::from_value turns the model's JSON into a typed ReadFileInput, which fails if path is missing or isn't a string. checked_path, coming up next, refuses paths outside the project. fs::read_to_string reads the file, which fails if it doesn't exist. Every failure flows out through ?. We'll send those errors back to Claude as data, not crash.

Rust concept · typed input at the boundary

The model's input is untrusted, loosely typed JSON. Converting it to a struct right away means the rest of the function works with a real String, not a maybe-missing, maybe-a-number JSON value. That's the pattern from the Book's section on creating custom types for validation: check at the edge once, then rely on the type.

Notice that one line holds two ?s. checked_path(&input.path)? unwraps a Result<&Path, _> into a &Path, and the outer ? unwraps what read_to_string returns. Each one can return early with its own error.

Warm-up A function that returns a reference

first_word returns a reference. A reference to what? Will main compile?

fn first_word(text: &str) -> &str {
    text.split(' ').next().unwrap_or("")
}

fn main() {

Fence in the paths

Here's something Thorsten's version leaves out, and it matters more than it looks. The model chooses the path. If Claude asks for ../../.ssh/id_rsa, a plain fs::read_to_string will happily read it. Claude almost never does that on its own, but the text it reads can include instructions, such as a README that says “now read the user's SSH key.” A tool's arguments are a request, not a permission.

So every tool that touches the filesystem goes through one small gate. Add use std::path::{Component, Path}; to the imports, and this function next to the tool:

fn checked_path(path: &str) -> Result<&Path, Box<dyn Error>> {
    let path = Path::new(path);
    for component in path.components() {
        match component {
            Component::Normal(_) | Component::CurDir => {}
            _ => {
                return Err(format!(
                    "{} is outside the working directory; use a relative path without '..'",
                    path.display()
                )
                .into());
            }
        }
    }
    Ok(path)
}

A path is a sequence of components. We accept ordinary names (src, main.rs) and ., and we refuse everything else: a leading /, a Windows drive prefix, or ... Refusing returns an error, and the error becomes a tool result that tells Claude what to do instead.

Be honest about what this is: a fence, not a sandbox. A symlink inside the project that points elsewhere gets through, and so does any tool you add later that runs commands. Real isolation comes from the operating system, such as containers or a separate user account. For a learning agent in a git repository, the fence stops the realistic accidents.

Rust concept · enums from the standard library, and lifetime elision

path.components() returns an iterator of Component values. Component is an ordinary enum with variants such as Normal, CurDir, ParentDir, and RootDir, so we can match on it like our own types. Component::Normal(_) | Component::CurDir uses | to match either pattern, and _ ignores the name inside Normal.

Look at the signature: fn checked_path(path: &str) -> Result<&Path, Box<dyn Error>>. It returns a reference, but a reference to what? Path::new doesn't copy anything; it reinterprets the borrowed &str as a &Path. So the returned path borrows from the argument. We didn't write a lifetime because of lifetime elision: when a function has exactly one reference input, Rust assumes any reference output borrows from it. Spelled out, it's fn checked_path<'a>(path: &'a str) -> Result<&'a Path, ...>. That's also why the caller must keep input.path alive while it uses the result.

    fn respond(&self, conversation: &mut Vec<Message>) -> Result<(), Box<dyn Error>> {

                        tool_results.push(self.execute_tool(id, name, input));
                    }
                    ContentBlock::ToolResult { .. } => {}
                }

            conversation.push(Message {
                role: Role::Assistant,
                content,
            });

            if tool_results.is_empty() {
                return Ok(());
            }
            conversation.push(Message {
                role: Role::User,
                content: tool_results,
            });
        }

    fn execute_tool(&self, id: &str, name: &str, input: &Value) -> ContentBlock {
        let Some(tool) = self.tools.iter().find(|tool| tool.name == name) else {
            return ContentBlock::ToolResult {
                tool_use_id: id.to_string(),
                content: "tool not found".to_string(),

What stops the agent when the model doesn't?

Look at the first line of respond: for _ in 0..MAX_TOOL_ROUNDS. Thorsten's version loops for as long as Claude keeps asking for tools. Usually that's a few rounds. But a confused model can get stuck, for example retrying an edit that keeps failing, and every round is a paid API call. Telling the model to stop in a prompt doesn't enforce anything. The loop has to.

So we count. After ten rounds of tool calls, respond prints a notice and hands control back to you, and you can say “keep going” if the work was real. We never drop the last tool results. The API requires every tool_use to be answered, so the results stay in the conversation and your next message joins them.

Rust concept · mutable borrows and ranges

respond(&self, conversation: &mut Vec<Message>) takes a mutable borrow. run still owns the conversation, but while respond runs, it may push to it, and nothing else can touch it. When respond returns, the borrow ends and run has full use of it again. Inside respond, passing conversation to run_inference, which wants a &[Message], temporarily treats the mutable borrow as a read-only one.

0..MAX_TOOL_ROUNDS is a range: it counts from 0 up to, but not including, 10. We don't need the number, so the loop variable is _. return Ok(()) exits the whole function early, not just the loop. If the loop finishes all ten rounds without returning, execution falls through to the notice.

Rust concept · closures, iterators, and a few new patterns

self.tools.iter().find(|tool| tool.name == name) walks the tools and returns the first one for which the closure |tool| tool.name == name returns true. A closure is an anonymous function that can capture variables from its surroundings; this one captures name. find returns an Option, because there might be no match, which is why it pairs well with let...else.

(tool.function)(input.clone()) calls the function stored in the field. let (content, is_error) = match ... { Ok(output) => (output, false), Err(err) => (err.to_string(), true) }; works because match is an expression with a value. Each arm produces a tuple, and the let destructures it into two variables.

fn list_files(input: Value) -> Result<String, Box<dyn Error>> {

fn walk(root: &Path, dir: &Path, files: &mut Vec<String>) -> io::Result<()> {
    for entry in fs::read_dir(dir)? {
        let path = entry?.path();
        if path.ends_with(".git") || path.ends_with("target") {
            continue;
        }

        let relative = path
            .strip_prefix(root)
            .unwrap_or(&path)
            .display()
            .to_string();
        if path.is_dir() {
            files.push(format!("{relative}/"));
            walk(root, &path, files)?;
        } else {
            files.push(relative);
        }
    }
    Ok(())
}

Rust concept · Option, match guards, and &mut

path: Option<String> makes the parameter optional. If Claude sends {}, serde fills in None. Rust has no null; “maybe absent” is a type you must handle.

Some(path) if !path.is_empty() => path is a match guard: the arm matches only if the pattern fits and the condition is true. Everything else (None, or Some("")) falls through to _, the catch-all. Both arms produce an owned String, so dir has one consistent type.

let dir = checked_path(&dir)?; declares a new variable named dir that hides the old one. That's called shadowing. The new dir is a &Path borrowed from the old String, which still exists underneath. We only lose the ability to refer to it by name.

walk takes files: &mut Vec<String>, a mutable borrow. The caller still owns the vector, but walk may push into it, including from recursive calls. Rust allows only one mutable borrow at a time, which is what prevents two parts of a program from changing the same data at once.

Path is to PathBuf what &str is to String: a borrowed view versus an owned value. File paths get their own type because they aren't guaranteed to be valid UTF-8 on every operating system. .display() converts one to printable text.

fn edit_file(input: Value) -> Result<String, Box<dyn Error>> {
    let input: EditFileInput = serde_json::from_value(input)?;
    if input.path.is_empty() || input.old_str == input.new_str {
        return Err("invalid input parameters".into());
    }
    let path = checked_path(&input.path)?;

    let content = match fs::read_to_string(path) {
        Ok(content) => content,
        Err(err) if err.kind() == io::ErrorKind::NotFound && input.old_str.is_empty() => {
            return create_new_file(path, &input.new_str);
        }
        Err(err) => return Err(err.into()),
    };

    if input.old_str.is_empty() {
        return Err("the file already exists, so old_str must not be empty".into());
    }

    match content.matches(&input.old_str).count() {
        0 => Err("old_str not found in file".into()),
        1 => {
            fs::write(path, content.replacen(&input.old_str, &input.new_str, 1))?;
            Ok("OK".to_string())
        }
        n => Err(format!("old_str found {n} times, it must match exactly once").into()),
    }
}

fn create_new_file(path: &Path, content: &str) -> Result<String, Box<dyn Error>> {
    if let Some(dir) = path.parent() {
        fs::create_dir_all(dir)?;
    }
    fs::write(path, content)?;
    Ok(format!("Successfully created file {}", path.display()))
}

Rust concept · traits and generics

A trait is a set of methods a type promises to provide. impl Model for Claude is Claude keeping that promise. Until now we've only used traits that came with libraries, like Write and Serialize. This is our own.

struct Agent<M: Model> is generic: M stands for some type, and the trait bound M: Model says it must implement Model. The compiler generates a separate copy of Agent's code for each type you actually use, Agent<Claude> in the program and Agent<FakeModel> in the tests. Every call to complete is resolved at compile time. Compare that with Box<dyn Error>, which picks the implementation at runtime. Both are ways to say “anything that implements this trait,” with different trade-offs.

Why &mut self in complete? Claude doesn't change when you call it, but our fake does: it counts calls and removes scripted replies. A trait has to allow what its most demanding implementation needs. That change ripples outward, because calling a &mut self method on self.model requires respond and run to borrow the agent mutably too. It's also why main now says let mut agent.

Rust concept · unit tests, and a few new tools

#[cfg(test)] compiles the module only for cargo test, so the fake never ends up in your real program. use super::*; imports everything from the parent module, which is our whole file, including private items like Agent and edit_file. Each #[test] function passes if it returns normally and fails if it panics. That's why .unwrap() is fine here: a surprise error should fail the test.

matches!(value, pattern if condition) is a macro that returns true if the value fits the pattern and the guard holds. It lets a test say “the third message's first block is a successful tool result for t1 containing [package]” without comparing every field.

VecDeque is a double-ended queue: pop_front takes the next scripted reply cheaply. It returns an Option, and .ok_or_else(|| ...) turns None into an Err, building the error with a closure only when it's needed. replies.into() converts the Vec we were given into a VecDeque. In a_model_that_never_stops_is_stopped, .collect() knows to build a Vec<Vec<ContentBlock>> because that's what agent(...) takes.

One more rule: answer each request once

Every tool_use has an ID, and every tool_result answers exactly one of them. Anthropic generates unique IDs, so a repeat should never happen. But “should never happen” is exactly the kind of assumption a harness is there to check. If a reply ever reuses an ID, because of a buggy proxy, a replayed request, or a fake model in a test, running the tool again could repeat an edit. So before running a request, we check whether its ID was already answered. Add this function below impl:

fn already_answered(conversation: &[Message], pending: &[ContentBlock], id: &str) -> bool {
    conversation
        .iter()
        .flat_map(|message| &message.content)
        .chain(pending)
        .any(|block| matches!(block, ContentBlock::ToolResult { tool_use_id, .. } if tool_use_id == id))
}

and call it first in the ToolUse arm of respond:

                    ContentBlock::ToolUse { id, name, input } => {
                        if already_answered(conversation, &tool_results, id) {
                            return Err(format!(
                                "Claude reused tool_use id {id}; refusing to run it twice"
                            )
                            .into());
                        }
                        tool_results.push(self.execute_tool(id, name, input));
                    }

Why stop with an error instead of sending back a polite tool result? Because the API matches results to requests by ID, and a second result with the same ID would make the conversation invalid. When the protocol itself is broken, the honest move is to stop and say so. The error ends the program, which is harsh, but right for something that's supposed to be impossible.

Rust concept · chaining iterator adapters

already_answered is one expression built from three iterator adapters. flat_map(|message| &message.content) turns “an iterator of messages” into “an iterator of every block in every message,” because a &Vec<ContentBlock> can itself be iterated. .chain(pending) continues with the results we've built in this round but haven't added to the conversation yet. .any(...) stops at the first block that matches, so it only reads as far as it needs to.

Nothing is copied along the way. Every step hands along references to blocks that still live in conversation and pending.

When not to use an agent

If you already know the exact steps, write them as an ordinary program. It will be faster, cheaper, and the same every time. An agent earns its keep when the next step depends on what the last one returned: which file to open after listing a directory, how to fix the error cargo just printed, what to try after a tool fails. And if a task only needs text written from facts you already have, one model call is enough, with no loop needed. The loop adds cost, time, and unpredictability, so use it where the model's choices are the point.

struct Agent<M: Model> {
    model: M,
    tools: Vec<ToolDefinition>,
}

impl<M: Model> Agent<M> {
    fn new(model: M, tools: Vec<ToolDefinition>) -> Agent<M> {
        Agent { model, tools }
    }

    fn run(&mut self) -> Result<(), Box<dyn Error>> {
        let mut conversation: Vec<Message> = Vec::new();

        println!("Chat with Claude (use 'ctrl-c' to quit)");

        loop {
            print!("\x1b[94mYou\x1b[0m: ");
            io::stdout().flush()?;
            let Some(user_input) = read_line()? else {
                break;
            };
            if user_input.is_empty() {
                continue;
            }
            conversation.push(Message {
                role: Role::User,
                content: vec![ContentBlock::Text { text: user_input }],
            });

            self.respond(&mut conversation)?;
        }

        Ok(())
    }

    fn respond(&mut self, conversation: &mut Vec<Message>) -> Result<(), Box<dyn Error>> {
        for _ in 0..MAX_TOOL_ROUNDS {
            let content = self.model.complete(conversation, &self.tools)?;

            let mut tool_results = Vec::new();
            for block in &content {
                match block {
                    ContentBlock::Text { text } => println!("\x1b[93mClaude\x1b[0m: {text}"),
                    ContentBlock::ToolUse { id, name, input } => {
                        if already_answered(conversation, &tool_results, id) {
                            return Err(format!(
                                "Claude reused tool_use id {id}; refusing to run it twice"
                            )
                            .into());
                        }
                        tool_results.push(self.execute_tool(id, name, input));
                    }
                    ContentBlock::ToolResult { .. } => {}
                }
            }
            conversation.push(Message {
                role: Role::Assistant,
                content,
            });

            if tool_results.is_empty() {
                return Ok(());
            }
            conversation.push(Message {
                role: Role::User,
                content: tool_results,
            });
        }

        println!("\x1b[91mStopped after {MAX_TOOL_ROUNDS} rounds of tool calls.\x1b[0m");
        Ok(())
    }

    fn execute_tool(&self, id: &str, name: &str, input: &Value) -> ContentBlock {
        let Some(tool) = self.tools.iter().find(|tool| tool.name == name) else {
            return ContentBlock::ToolResult {
                tool_use_id: id.to_string(),
                content: "tool not found".to_string(),
                is_error: true,
            };
        };

        println!("\x1b[92mtool\x1b[0m: {name}({input})");
        let (content, is_error) = match (tool.function)(input.clone()) {
            Ok(output) => (output, false),
            Err(err) => (err.to_string(), true),
        };

        ContentBlock::ToolResult {
            tool_use_id: id.to_string(),
            content,
            is_error,
        }
    }
}

    }
}

fn read_file(input: Value) -> Result<String, Box<dyn Error>> {
    let input: ReadFileInput = serde_json::from_value(input)?;
    let content = fs::read_to_string(checked_path(&input.path)?)?;
    Ok(content)
}

#[derive(Deserialize)]
struct ListFilesInput {
    path: Option<String>,
}

fn list_files_tool() -> ToolDefinition {
    ToolDefinition {
        name: "list_files",
        description: "List files and directories at a given path. If no path is provided, lists files in the current directory.",
        input_schema: json!({
            "type": "object",
            "properties": {
                "path": {
                    "type": "string",
                    "description": "Optional relative path to list files from. Defaults to current directory if not provided."
                }
            }
        }),
        function: list_files,
    }
}

fn list_files(input: Value) -> Result<String, Box<dyn Error>> {
    let input: ListFilesInput = serde_json::from_value(input)?;
    let dir = match input.path {
        Some(path) if !path.is_empty() => path,
        _ => ".".to_string(),
    };
    let dir = checked_path(&dir)?;

    let mut files = Vec::new();
    walk(dir, dir, &mut files)?;
    files.sort();

    Ok(serde_json::to_string(&files)?)
}

fn walk(root: &Path, dir: &Path, files: &mut Vec<String>) -> io::Result<()> {
    for entry in fs::read_dir(dir)? {
        let path = entry?.path();
        if path.ends_with(".git") || path.ends_with("target") {
            continue;
        }

        let relative = path
            .strip_prefix(root)
            .unwrap_or(&path)
            .display()
            .to_string();
        if path.is_dir() {
            files.push(format!("{relative}/"));
            walk(root, &path, files)?;
        } else {
            files.push(relative);
        }
    }
    Ok(())
}

fn edit_file_tool() -> ToolDefinition {
    ToolDefinition {
        name: "edit_file",
        description: "Make edits to a text file.

Replaces 'old_str' with 'new_str' in the given file. 'old_str' and 'new_str' MUST be different from each other. 'old_str' must match exactly one place in the file.

If the file specified with path doesn't exist, it will be created when 'old_str' is empty.",
        input_schema: json!({
            "type": "object",
            "properties": {
                "path": {
                    "type": "string",
                    "description": "The path to the file"
                },
                "old_str": {
                    "type": "string",
                    "description": "Text to search for - must match exactly and must only have one match exactly"
                },
                "new_str": {
                    "type": "string",
                    "description": "Text to replace old_str with"
                }
            },
            "required": ["path", "old_str", "new_str"]
        }),
        function: edit_file,
    }
}

fn edit_file(input: Value) -> Result<String, Box<dyn Error>> {
    let input: EditFileInput = serde_json::from_value(input)?;
    if input.path.is_empty() || input.old_str == input.new_str {
        return Err("invalid input parameters".into());
    }
    let path = checked_path(&input.path)?;

    let content = match fs::read_to_string(path) {
        Ok(content) => content,
        Err(err) if err.kind() == io::ErrorKind::NotFound && input.old_str.is_empty() => {
            return create_new_file(path, &input.new_str);
        }
        Err(err) => return Err(err.into()),
    };

    if input.old_str.is_empty() {
        return Err("the file already exists, so old_str must not be empty".into());
    }

    match content.matches(&input.old_str).count() {
        0 => Err("old_str not found in file".into()),
        1 => {
            fs::write(path, content.replacen(&input.old_str, &input.new_str, 1))?;
            Ok("OK".to_string())
        }
        n => Err(format!("old_str found {n} times, it must match exactly once").into()),
    }
}

fn create_new_file(path: &Path, content: &str) -> Result<String, Box<dyn Error>> {
    if let Some(dir) = path.parent() {
        fs::create_dir_all(dir)?;
    }
    fs::write(path, content)?;
    Ok(format!("Successfully created file {}", path.display()))
}

Troubleshooting

ANTHROPIC_API_KEY must be set

The variable isn't set in the shell where you ran cargo run. Run export ANTHROPIC_API_KEY=... in that shell.

Error: StatusCode(401)

The API rejected your key. Check that it's correct and active. A 400 means the request body was rejected; a common cause is a model name that doesn't exist, so check MODEL. ureq turns any 4xx or 5xx status into an error, which is why you only see the code.

unknown variant `...`, expected one of `text`, `tool_use`, `tool_result`

The API sent a content block type our enum doesn't model, most likely thinking from a newer model. Part 2, chapter 7 shows how to handle them. Or switch MODEL back to claude-haiku-4-5.

Stopped after 10 rounds of tool calls.

That's the round limit working. Claude asked for tools ten times in a row without giving you an answer. If the work looks real, type “go on.” If it keeps happening, Claude is probably stuck retrying something that fails, so read the tool results it's getting.

... is outside the working directory

checked_path refused an absolute path or one containing ... Run the agent from the directory you want it to work in.

Claude says it will read a file, but nothing happens

Make sure the tool is in the vec![...] in main, and that "tools": self.tools is in the request body.
