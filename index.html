Why does a model need a harness?

Suppose you ask, "If I buy 5 washers, how many will I have?" Before adding anything, the program needs to find out how many washers you have now.

That count lives in your inventory. For our exercise, it's a single in-memory record containing 12. A model can't read the record on its own, so we need a way for it to ask our program for the value. A sentence such as "I checked your inventory" isn't enough; we want an actual lookup and a result we can inspect.

We'll give the model two tools, ordinary functions called lookup and add. The model requests a tool by returning its name and arguments as data. Our harness receives that request, checks whether it can run, calls the function, and sends the result back to the model. This is the connection we'll build throughout the course. The model proposes the next step; Rust code performs it.

By lesson 12, your offline agent will look up 12, add the proposed 5, and answer "12 washers + 5 = 17 washers." A small command-line program, the host, starts the run and prints the answer. It also saves a session so you can inspect the two tool calls and three model requests afterward. We're calculating a possible purchase, not making one, so stock stays at 12.

Why use a model at all?

You probably wouldn't use one for this question alone. A fixed program that calls lookup and then add would be easier to understand and test. And if a task only needs text based on facts already in its request, a single model call may be enough.

A harness becomes useful when you want a model to choose what to do next based on the task and the results so far. It might ask for a missing fact, try another available tool after an error, or answer once it has enough information. Returning each tool result to the model makes that possible, while the harness keeps control of permission and stopping rules.

To learn that control flow, we'll use a fake model that returns a fixed script. It won't interpret the question or adapt when stock changes, but it gives us repeatable tests without a network connection or unpredictable replies. Later, a real model can implement the same Model interface, handling provider translation and tool descriptions behind it. We can then evaluate its judgment separately from the loop we've already tested.

Follow the finished inventory run

Here's the run we're working toward. You don't need to run anything yet; follow how each result becomes input to the next request. These steps come from the lesson 12 script and capstone test. The test shortens our question to "If I buy 5 washers, how many?" The fake returns the same script either way because it doesn't parse the question.

  1. The host starts the run. It supplies that shorter question, the inventory registry, and limits of 3 model attempts and 2 tool executions. The harness stores User("If I buy 5 washers, how many?"). With default context selection disabled, request 1 contains only this message.
  2. The model proposes lookup. Scripted reply 1 is Call(c1, lookup, item=Text("washers")). The harness validates the reply and new ID, finds lookup, validates item, checks host permission, then checks stop conditions and execution budget. The tool reads the toy record and returns Ok(12). The harness appends Assistant(call c1) and Tool(call_id=c1, name=lookup, outcome=Ok(12)).
  3. The harness asks again with evidence. Request 2 contains the User message, assistant call c1, and lookup observation. The fake returns Call(c2, add, a=Int(12), b=Int(5)). Those operands are hard-coded in the fixture. A real model would need to choose them from the question and observation.
  4. The harness dispatches addition. It applies the same checks before add executes. The function returns Ok(17). The harness appends Assistant(call c2) and Tool(call_id=c2, name=add, outcome=Ok(17)). Request 3 now contains five messages, including both call-and-result pairs.
  5. The model supplies final text. The script returns Final("12 washers + 5 = 17 washers."). The harness appends that reply and stops with Final status, 3 attempts, 2 executions, and 6 messages. The host prints the result. It can save the completed events and compare a replay without executing either tool again.

Notice that the messages carry results back to the model. From lesson 5 onward, we'll also keep an event trace for ourselves. ModelRequested and ModelReplied record the requests and replies, while ToolStarted and ToolFinished show which operations ran and what they returned. A rejected call gets ToolRejected instead. RunStarted and RunFinished mark the beginning and end, giving us a record to inspect or replay.

What if the final answer sounds right but the lookup never ran? Final is a stopping signal, not proof of a correct answer. That's why the capstone checks the observations and later requests as well as the text. Try changing stock to 99 without changing the script: it still claims 17. It can make the same claim when permission denies both tools. We'll use those experiments to check the answer against the evidence.

The return path also carries errors. Unknown or invalid calls produce error observations, as does a tool that executes and fails. A real model could use an error to choose a different next step; our fake keeps following its script. In lesson 6 we'll decide when the harness must stop instead, using budgets, cancellation, and deadlines.

Rust concepts for this lesson

Read a function signature

Put the unfinished add starter from setup in src/lib.rs. Put its test in tests/acceptance.rs. These are two files in the same Cargo project, not two programs to paste together.

Read pub fn add(a: i64, b: i64) -> i64 { ... } one part at a time.

  • fn starts a function definition. add is the name used to call it.
  • a: i64 names a parameter and its type. i64 is a signed 64-bit whole number. The comma separates the two parameters.
  • -> i64 declares the value returned to the caller. Rust checks both argument and return types before execution.
  • The braces contain the body, the code that runs when called.
  • pub makes this library function accessible to outside callers, including the integration test.

The ! marks a macro invocation, which expands into Rust code. todo!("...") is a placeholder macro. It compiles, but panics when execution reaches it. println! and assert_eq! are macros too.

Return a value in three ways

Worked program · tail expression

fn seven() -> i64 {
    7
}
fn main() {
    assert_eq!(seven(), 7);
}

Notice that the 7 has no semicolon after it. In Rust, the final expression in a block supplies that block's value, so calling seven gives 7 back to main. You don't need to write return for this form. Next, let's compare it with an explicit return.

Worked program · explicit return, independent of the previous program

fn seven() -> i64 {
    return 7;
}
fn main() {
    assert_eq!(seven(), 7);
}

This time, return tells Rust to leave the function with 7. The semicolon ends the return statement without discarding the value being returned. Both programs give the caller the same result; the next version gives that result a local name first.

Worked program · local binding

fn seven() -> i64 {
    let total = 7;
    total
}
fn main() {
    assert_eq!(seven(), 7);
}

Here, let total = 7; gives the value a name before we return it. That statement ends with a semicolon, but the final total expression doesn't, so the function still returns 7. If your usual language requires an explicit return, this may look unfamiliar. Try reading the last line as the value the caller receives. The binding also stays unchanged unless you declare it with mut.

Deliberately broken program · do not keep this version

fn seven() -> i64 {
    7;
}
fn main() {}

This version won't compile. Read the mismatch in E0308: the signature promises i64, but the body produces (). The semicolon discards 7 and leaves the block with unit, (), Rust's value for no meaningful result. A function without a declared return type returns unit too. Remove the semicolon here and the body supplies the number its signature promises.

What data should the harness own?

The conversation needs to survive across requests, so the harness will own it. The model only needs to read the messages while preparing a reply, which means it can borrow them instead. Rust concepts for this lesson

Own, borrow, or copy

Suppose you have some text and want to give it to another part of the program. With a String or Vec, Rust keeps track of which binding owns the value and will drop it when it's no longer needed. Assigning that value to a new binding, or passing it by value, moves ownership rather than making an independent copy. You then use the new owner; to keep two independent values, you must explicitly clone.

We don't always need to hand ownership over. A String owns growable UTF-8 text, while &str lets another part of the program read the text through a borrowed view. Rust prevents conflicting mutation while that shared borrow is still in use. Integers such as i64 work differently: they implement Copy, so assignment copies the value and leaves both names usable. The following program puts these cases side by side.

Worked program · tiny values before conversation data

fn main() {
    let label = String::from("hi");
    let view = &label;
    assert_eq!(view, "hi");
    assert_eq!(label, "hi");
    let moved = label;
    assert_eq!(moved, "hi");

    let count: i64 = 2;
    let copied = count;
    assert_eq!(count, 2);
    assert_eq!(copied, 2);
}

The program passes every assertion without printing anything. Look at the move halfway through: the earlier assertions can use both the borrow and the original string because the borrow's last use comes before ownership changes. After the move, only the new owner can use the string. Adding println!("{}", label); there produces E0382. The integer assertions both pass because assignment copied the number instead of moving it.

Those ownership choices now give us a way to design the conversation. Messages will store owned String values so their text can survive the call that created them, while functions that only read temporary input can accept &str. The conversation itself is a Vec<Message>, an ordered collection that can grow. When the model reads it, we'll pass &[Message], a borrowed slice that leaves ownership with the caller and doesn't allow changes through the slice.

Choose a shape for each value

A struct groups named fields that exist together. Below, a Call has an id, a name, and args. Construct it with braces and field names. pub on each field lets integration tests inspect it.

A model reply might be a final answer or a request for a tool. We'll use an enum to describe those alternatives, called variants. For a smaller example, Scalar::Int(2) holds an integer, whereas Reply::Final("5".into()) holds final text. The .into() conversion produces the String that the Final variant needs, and the parentheses hold that variant's value.

Result<T, E> is either Ok(value) of type T or Err(error) of type E. For example, Ok(5) can be a successful tool result. Err(ModelError::Exhausted) names a failure rather than panicking.

Option<T> is either Some(value) or None. It describes an optional value without an error reason. An empty reply queue returns None; the fake converts that absence to a named Err.

Read the type declarations

use std::collections::BTreeMap; imports a standard-library map type. A BTreeMap<String, Scalar> maps text keys to scalar values in key order. pub type RawArgs = ...; gives that existing type a public alias, not a new wrapper type.

#[derive(Debug, Clone, PartialEq, Eq)] asks the compiler to generate trait implementations. PartialEq compares values and Debug displays them when assert_eq! fails. Eq marks equality where each value equals itself. Clone permits an explicit owned copy. The strings and collections here clone their contents; use that intentionally for fake request snapshots, not to hide a misplaced borrow.

Read an enum with match

Before writing reply validation, let's read a smaller enum. A label is either blank or holds some text. We want a function that returns the text's length without taking ownership of the label.

Worked match example · standalone program

enum Label {
    Blank,
    Text(String),
}

fn byte_count(label: &Label) -> usize {
    match label {
        Label::Blank => 0,
        Label::Text(text) => text.len(),
    }
}

fn main() {
    let label = Label::Text(String::from("oak"));
    assert_eq!(byte_count(&Label::Blank), 0);
    assert_eq!(byte_count(&label), 3);
    println!("{} bytes", byte_count(&label));
}

Both assertions pass, and the program prints 3 bytes.

Each line inside match is an arm. The pattern before => describes a case, and the expression after it supplies that case's value. Commas separate the arms. Rust checks the patterns in order and runs the first matching arm.

The pattern Label::Text(text) opens the Text variant and gives its field the local name text. This is called destructuring. Because we're matching &Label, Rust binds that field as &String, a shared borrow. Calling text.len() reads its UTF-8 byte count without moving the string. That's why main can borrow the same label again for printing.

A match is an expression, so its chosen arm produces a value. Both arms here produce a usize. There is no semicolon after the match, so that value becomes the function's return value, just like the addition expression in lesson 1. If an arm needs several statements, put them in braces and leave its final value without a semicolon.

The match is exhaustive because it handles both variants. Remove the Blank arm and the compiler reports E0004, even though the label in main holds Text. Restore the arm before continuing. Listing every variant makes Rust point out missing cases if the enum changes later. Use the same approach to inspect a borrowed Reply in your validation function.

Repeat work within a limit

A for loop can repeat work a bounded number of times. Before connecting the model, try this smaller program that prints page numbers and stops when it reaches the last page.

Worked bounded loop · standalone program

fn print_pages(limit: usize, last_page: usize) -> usize {
    let mut printed = 0;
    for index in 0..limit {
        let page = index + 1;
        println!("page {}", page);
        printed += 1;
        if page == last_page {
            break;
        }
    }
    printed
}

fn main() {
    let printed = print_pages(4, 2);
    assert_eq!(printed, 2);
    println!("printed {} pages", printed);
    assert_eq!(print_pages(0, 2), 0);
    assert_eq!(print_pages(1, 2), 1);
}

The assertions pass. The program prints these four lines.

page 1
page 2
printed 2 pages
page 1

The range 0..limit includes zero and excludes limit. With a limit of 4, it can yield 0, 1, 2, and 3. The for loop binds each successive value to index and runs the body once for that value. Adding one gives us page numbers starting at 1.

The counter needs mut because printed += 1 changes it after each page. When the page number equals last_page, break; exits the loop immediately. It does not return from the function. Execution continues after the loop, where the final expression returns the counter.

The first call stops after page 2, before using all four iterations. A zero limit gives an empty range, so the second call prints nothing and returns zero. The third call prints only page 1 because its range ends before page 2. The limit bounds work even when the stopping condition is never reached.

use std::fs::{File, OpenOptions};
use std::io::{self, Read, Write};
use std::path::Path;

pub fn read_small(path: &Path) -> io::Result<Vec<u8>> {
    const LIMIT: u64 = 1024 * 1024;
    let file = File::open(path)?;
    let mut bytes = Vec::new();
    file.take(LIMIT + 1).read_to_end(&mut bytes)?;
    if bytes.len() as u64 > LIMIT {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData, "session exceeds 1 MiB",
        ));
    }
    Ok(bytes)
}
pub fn write_new(path: &Path, bytes: &[u8]) -> io::Result<()> {
    let mut file = OpenOptions::new()
        .write(true).create_new(true).open(path)?;
    file.write_all(bytes)
}

Importing Read makes take and read_to_end available; Write does the same for write_all. The detail to notice is that take allows one byte beyond our limit. If we stopped reading at exactly 1 MiB, we couldn't distinguish a file of that size from a longer file whose tail we'd ignored. Reading the extra byte lets the helper accept exactly 1 MiB and reject anything larger with InvalidData. Decoding and history validation still come after this size check.

Using create_new(true) protects an existing session by refusing to open a destination that already exists. A new write can still fail partway through and leave a partial file, so this isn't an atomic-write guarantee. The helper returns the error to the host, which decides how to report it.

pub struct WireAdapter<F> {

where
    F: FnMut(&[Message]) -> Result<String, ModelError>,

        Self { transport }

use std::{error::Error, fmt};
#[derive(Debug)]
struct EmptyName;
impl fmt::Display for EmptyName {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "name is empty")
    }
}
impl Error for EmptyName {}
fn require_name(name: &str) -> Result<(), EmptyName> {
    if name.is_empty() { Err(EmptyName) } else { Ok(()) }
}
fn host(name: &str) -> Result<(), Box<dyn Error>> {
    require_name(name)?;
    Ok(())
}
fn main() {
    assert_eq!(EmptyName.to_string(), "name is empty");
    assert!(host("washers").is_ok());
    assert_eq!(host("").unwrap_err().to_string(), "name is empty");
}

Assertions pass with no output. The formatter borrows an output destination; write! writes into it instead of printing to the terminal. '_ asks Rust to infer the borrow lifetime. Types by module
types.rs defines Message, Reply, Call, Scalar, RawArgs, Observation, ModelError, and ToolError. model.rs defines Model, FakeModel, scripts, and validate_reply. tools.rs defines Tool, Registry, validation, and inventory_registry. harness.rs defines run, RunOptions, RunResult, and Status. trace.rs defines Event and EventKind. Outcome rules
Only Final has result text. Every other status has empty text. An Err from the model becomes Status::ModelError. If harness validation rejects a typed reply, return ProtocolError. Record tool failures as observations. Use Result for expected failures. A programming bug may panic and fail a test. The harness does not recover from panics or retry automatically.
Validation order
Validate the reply and check that its call ID is unique within the run before dispatch. Then look up the tool, validate arguments, check permission, check cancellation and the deadline, check the execution budget, and execute. Unknown, invalid, and denied calls do not count as executions. Each model attempt counts even if it fails. Addition arguments must be between -1,000,000 and 1,000,000 inclusive. Lookup item names must contain 1 to 40 UTF-8 bytes.
Message pairing
Append each accepted assistant call before its observation, keeping the same ID and name. Reject reused IDs before a second execution. A Final run must have no pending call. Budget, Deadline, and Cancelled may leave one accepted call that never started. In a completed session, every started tool must have an outcome, even if the run stops immediately after the tool returns.
Replay consistency
Validate the order of model requests and replies, unique call IDs, tool starts and outcomes, observation names, and the single terminal event. The terminal turn count must equal the number of ModelRequested records. The execution count must equal the number of ToolStarted records. Final text must match the last accepted Final reply. ContextSelected records which messages a request used without changing the stored transcript. Reconstruct the run only after validation succeeds.
Serialization boundary
Use serde's externally tagged enums, reject unknown fields, and set the Session version to 1. Decoding checks data types and fields. validate_session checks whether the events describe a valid history. Accept input files of at most 1 MiB and streamed replies of at most 16,384 bytes. These are exercise limits, not recommended defaults for every production system.
